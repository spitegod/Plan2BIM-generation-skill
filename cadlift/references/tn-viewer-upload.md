# Загрузка готовой модели в TN-Viewer

После проверки модели сохранять её локально и отправлять в коллекцию владельца токена. Текущее указание пользователя имеет приоритет: при явном запросе «только локально» загрузку пропустить. Передавать готовую модель, её необходимые зависимости и превью; исходные DWG, рабочие FCStd, скрипты, логи и прочие файлы проекта не загружать автоматически.

## Адрес и авторизация

- Сервер по умолчанию: `https://185.246.64.165`.
- Коллекция: `https://185.246.64.165/website/collection.html`.
- Исходный код и контракт: [TN-Viewer, server/README.md](https://github.com/spitegod/TN-Viewer/blob/main/server/README.md), раздел «API для Codex». Контракт проверен на сервере12.11.2026.
- Авторизация: HTTP-заголовок `Authorization: Bearer <TOKEN>`.

Использовать действующий токен, уже переданный пользователем в текущем чате для этого сервера. Не запрашивать его повторно без причины. Если токена в чате нет, задать короткий вопрос: «Пришлите токен API TN-Viewer для загрузки модели в вашу коллекцию». Пока ответа нет, продолжать генерацию, проверку и локальное сохранение; загрузка остаётся незавершённой. При недействительном или отозванном токене запросить новый.

Токен не сохранять в SKILL.md, справочных материалах, конфигурациях, скриптах, отчётах, ZIP, URL или выводе команд. Передавать его инструменту выполнения только для авторизации запроса к указанному серверу, используя временное значение в памяти/окружении без вывода. Не искать токены в других чатах, файлах или учётных записях. При переносе скилла другой пользователь предоставляет свой токен. Проверку TLS не отключать.

Использовать HTTP API напрямую. Computer Use, клики в браузере и вход через страницу сайта для загрузки не нужны: токен ограничен маршрутами `/api/models`, поэтому `/website/` с этим токеном может возвращать401 при рабочем доступе к API.

## Последовательность

1. Выполнить `GET /api/models` с авторизацией. Успех —200 и список моделей. Это одновременно проверка токена и исходное состояние коллекции для защиты от дублей.
2. Подготовить PNG-превью готовой модели, соответствующее загружаемой версии: обе стороны не больше1024пикселей, файл не больше2МиБ. Использовать проверенный локальный рендер CAD-модели. Не подставлять изображение другой версии.
3. Выполнить `POST /api/models` с `multipart/form-data`:

   | Поле | Содержание |
   |---|---|
   | `name` | Понятное название узла и при необходимости версия |
   | `mainFile` | Точное имя основного файла, например `junction.glb` |
   | `preview` | PNG-файл превью |
   | `files` | Основной файл; поле повторяется для необходимых зависимостей |

   Для GLB с встроенными текстурами достаточно одного основного файла. Лимит всего запроса —256МиБ, включая multipart. Не уменьшать геометрическую детализацию ради лимита молча. Если сервер отклонил формат или объём, сохранить локальный результат, сообщить конкретную ошибку и определить поддерживаемый вариант.

4. Ожидать201 и JSON с `id`, `name`, `mainFile`, `createdAt`, `files`, `previewUrl`. Сохранить несекретные сведения о результате в рабочем отчёте модели.
5. Повторить `GET /api/models` и найти запись по возвращённому `id`; сверить название, основной файл и ссылки файлов/превью. Только после этого считать загрузку завершённой.
6. В ответе дать ссылку на локальную модель и коллекцию с названием загруженной модели. Если загрузка не выполнена, прямо сообщить причину, не смешивая её статус с успешным локальным сохранением.

При тайм-ауте POST или неоднозначном ответе сначала проверить коллекцию относительно исходного списка: запрос мог завершиться на сервере. Не отправлять файл повторно вслепую. Не перезагружать ту же версию в рамках одной задачи после подтверждённого успеха. При новой исправленной версии использовать различимое название и не удалять предыдущую автоматически.

Загрузка в личную коллекцию не требует создания общего доступа. Маршруты `/share`, `/delete`, выпуска токенов и администрирования использовать только по отдельному явному запросу пользователя. Не выполнять дополнительные загрузки для проверки правок этого скилла: уже подтверждённый контракт достаточен для документирования процесса.
